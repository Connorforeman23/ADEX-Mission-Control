# Package 1.3 — Implement the agreed access model — evidence

Assessment 11 Aug 2026. Decisions recorded in `ACCESS_MATRIX.md`. App-code only —
**no schema or RLS change** (the RLS model from the baseline was already correct;
1.3 makes the restricted experience graceful and closes the owner-assignment gap).

## What changed (all in `src/`)
- `lib/actions.ts` — restricted users are refused from booking/editing campaigns
  with a clear message (`createCampaign`, `updateCampaign`); their new leads,
  contacts and creative items are auto-owned by them (`ownerFor`).
- `components/CampaignTable.tsx`, `app/(app)/campaigns/page.tsx` — "New campaign"
  button hidden and `?new=1` deep-link neutralised for restricted users.
- `components/QuickNew.tsx`, `app/(app)/page.tsx` — the "+ New" menu drops the
  Campaign option for restricted users.
- `docs/ACCESS_MATRIX.md` — finalised from draft to agreed.

Two layers: the UI hides what a restricted user can't do; the **server actions
are the authoritative refusal** (a hidden button is not a security control).

## Dev test plan (restricted role not yet in production)
Create a restricted test user on dev and verify:

| Check | Expected |
|---|---|
| Nav for restricted user | No Finance / Reports / Settings (Measure group hidden) |
| Visit /finance or /reports directly | Redirected away (page guard) |
| "+ New" menu | No "Campaign" option |
| /campaigns page | No "New campaign" button |
| Visit /campaigns?new=1 directly | Booking panel does NOT open |
| Create a lead/contact | Saves, owned by the restricted user, and they can see it |
| Existing seed data (Acme, Example) | NOT visible to the restricted user (owned by others/nobody) |
