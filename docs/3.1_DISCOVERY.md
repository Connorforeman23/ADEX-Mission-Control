# Phase 3.1 — Organisation/Contact restructure — discovery

**Read-only discovery (11 Aug 2026).** Tests the proposed "Organisation as master
entity" model against how the system actually works today. No schema change.

---

## 1. How the "company" concept exists today

There is **no single company entity.** What the proposal calls an *Organisation*
is currently spread across **three places, plus free text**:

| Today | Table | Represents | Key fields |
|---|---|---|---|
| Customer | `clients` | trading customers only | `name` (UNIQUE), sector, owner_id, status (`live`/`plan`/`hold`), retainer, client_since, review_date |
| Prospect | `leads` | pipeline opportunities | `name` (NOT unique), contact (free text), sector, value, stage (`Engaged`/`Proposal`/`Closed Won`/`Closed Lost`), owner_id |
| Supplier | *(none)* | — | media owners exist only as free-text `campaign_lines.vendor` + a hard-coded roster in `reference.ts` |
| Company-on-a-contact | `contacts.organisation` | free-text company name | plus optional `client_id` and `lead_id` FKs |

So a single real company (e.g. Randox) can simultaneously exist as: a `clients`
row, a `leads` row, and a free-text string on many `contacts` — with no guaranteed
link between them.

---

## 2. Findings against the discovery questions

**Q: Companies acting as both client and supplier.**
Structurally **impossible to represent today** — clients are rows, suppliers are
text. So there's no clean data modelling it, but there's also nothing stopping the
same company being a `clients` row *and* a `vendor` string. Needs a data check
(query pack, §4) to see how often client names coincide with vendor names
(e.g. ITV, News UK, Reach appear as suppliers and could also be clients).

**Q: Current implicit prospect/client statuses.**
Three separate, incomplete status vocabularies, none matching the proposed lifecycle:
- `clients.status` = live / plan / hold
- `leads.stage` = Engaged / Proposal / Closed Won / Closed Lost
- `contacts.status` = Prospect / Engaged / Client / Lapsed

There is **no "Former Client" concept** and **no "Not Pursuing"** — a lost prospect
is a `Closed Lost` lead; a lapsed client has no clear home (`hold`?). No status-change
history exists (though 1.5's audit log now records raw changes to these tables).

**Q: Supplier records represented as clients.**
Possible but unconfirmed — some `clients` rows could actually be media-owner
suppliers mis-filed. Query pack checks client names against the known supplier
roster.

**Q: Contacts used independently of their company.**
**Yes, by design.** `contacts.organisation` is free text and a contact needs no
link to any `clients`/`leads` row. Contacts can have a company name that matches
no client and no lead, or be linked to a lead but not a client (or vice versa).
This is the biggest data-cleaning surface for the migration.

**Q: Financial records where `client_id` isn't really "client".**
`campaigns.client_id`, `client_invoices.client_id`, `creative_items.client_id` all
reference `clients` and genuinely mean *customer*. So the meaning is honest today.
**But** `clients` rows are auto-created from won leads by name-match
(`promoteWonLead` in `actions.ts`), so some client rows are thin/auto-generated and
may duplicate a lead or a differently-spelled contact organisation.
Note: **supplier POs are numbered by the *client's* initials** (e.g. `RAN0097` for
a Randox campaign), even though a PO is a supplier document — a client/supplier
conflation worth deciding on in 3.2.

**Q: Existing task/activity structures.**
`tasks` exists and links to campaign_id, client_id, lead_id, creative_id,
assignee_id, created_by — but **not** to a contact and not to an organisation
directly. There is **no activity/communication table at all** (greenfield for the
future email-sync timeline).

**Q: Dependencies that complicate the migration.**
See §3 — the security programme is the big one.

---

## 3. The biggest dependency: the security controls are bound to today's tables

Everything we built in 1.3–1.5 is coupled to the **current** table names and to
`client_id`/`owner_id`. A restructure to `organisations` must **carry these
forward**, not lose them:

- **1.3 access model (RLS):** policies on clients, campaigns, campaign_lines, leads,
  creative_items, contacts, invoices use `is_restricted()`, `owner_id`, and
  `can_see_client(client_id)`. Merging clients+leads into organisations means
  re-deriving all of this for `organisation_id`/organisation ownership.
- **1.4 integrity:** constraints on the financial tables mostly stay (those tables
  don't change), but any repointed FK needs re-checking.
- **1.5 audit:** triggers sit on `clients` and `leads`; they must move to
  `organisations` and the new status-history.

**This is the main technical risk and cost of Phase 3** — the restructure is as much
a security-re-homing exercise as a data one. It must be budgeted into 3.2/3.3.

## 4. Data-level questions only the live data can answer

The structure above is certain from the code. The *data* facts below need queries
against production (read-only) — see `supabase/PHASE3_DISCOVERY.sql`:
1. Client names that also appear as supplier vendors (client+supplier overlap).
2. Company names appearing in **both** `leads` and `clients` (duplicate companies).
3. Contacts whose `organisation` text matches no client and no lead (orphans).
4. Contacts with neither `client_id` nor `lead_id` set.
5. Distribution of `clients.status`, `leads.stage`, `contacts.status`.
6. Counts: clients, leads, contacts, distinct vendors.

The results tell us how messy the merge will be (especially dedup, §5-D).

### Data results (production, 11 Aug 2026)
| Finding | Value |
|---|---|
| clients | 2 |
| leads | 2 |
| contacts | 0 |
| distinct supplier vendors | 7 |
| companies in both leads and clients | 0 |
| client names that are also vendor names | 0 |
| contacts orphaned / unlinked | 0 |

**Conclusion: the dedup cost is effectively nil.** ~4 company records + 7 supplier
names, no duplicates, no overlaps, no orphan contacts. The migration is small and
clean **now** — strongly recommend doing the restructure before real client/contact
data accumulates and makes it harder.

## 5. Challenges & additions to the proposed business model

Broadly the model is sound and the instinct to keep it explicit (no generic
`entities`) is right. Specific points for 3.2:

- **A. Re-home the security controls (biggest one).** Treat the RLS access model,
  audit triggers, and integrity constraints as first-class migration deliverables,
  not an afterthought. The restructure that ignores them would silently drop the
  protections we just built.
- **B. Purpose-built status history, not the audit log.** The 1.5 audit log records
  raw changes but is admin-only JSON and has no "reason". Build a dedicated
  `organisation_customer_status_history` (old, new, at, by, reason) as the proposal
  suggests; keep the audit log as a secondary safety net.
- **C. Dedup is the real cost.** The same company exists today across leads, clients
  and free-text contact orgs, with spelling variance. Merging needs a matching pass
  with **human sign-off** (Rick/Connor), not an automated name-merge. Plan for it.
- **D. Suppliers need more than Yes/No.** Today suppliers carry an implicit *channel*
  (the roster is per-channel) and a free-text `supplier_contact`. Decide in 3.2
  whether supplier organisations carry channel tags and proper supplier contacts.
- **E-bis. A unique organisation identifier to prevent *future* duplicates.**
  Require a genuinely unique key on organisations — ideally a **Companies House
  number** (unique per legal entity, and auto-verifiable against the free Companies
  House API later) or a **website domain**; a postal address is a useful human aid
  but not a reliable key (multi-office companies, shared addresses, format variance).
  Suggest requiring it at the *Active Client* stage, optional at first prospect
  entry, to avoid data-entry friction. NB: this stops *new* duplicates only — the
  existing records carry no such identifier, so the one-time human dedup (point C)
  is still required.
- **E. Keep explicit relationship columns (agree strongly).** `campaigns.client_org_id`,
  `client_invoices.client_org_id`, `supplier_invoices/PO.supplier_org_id` — not a
  generic `organisation_id`. Preserves meaning *and* keeps the security model
  derivable per relationship.
- **F. Resolve status vocabulary overlap.** `contacts.status`
  (Prospect/Engaged/Client/Lapsed) partly duplicates the new org customer-status.
  Decide whether contact-level status survives or is derived from the organisation.
- **G. Archiving ≠ lifecycle (agree).** Add `archived boolean` distinct from customer
  status. Today there's no archive; `clients.status = 'hold'` is sometimes used as an
  informal one — clarify and migrate deliberately.
- **H. Pick one term.** The proposal uses both "customer" and "client". Choose one
  consistently to avoid the very ambiguity it warns against.
- **I. PO numbering.** POs are currently numbered by client initials. Under
  "PO → supplier organisation", decide whether that convention stays (grouping POs by
  client campaign) or moves to supplier-based numbering.

## 6. Recommended shape for 3.2 (for Rick & Connor to firm up)

- One `organisations` table: name, sector, owner_id, `is_supplier` (bool),
  `customer_status` (enum incl. "No customer relationship"), `archived` (bool).
- `organisation_customer_status_history` for tracked status changes.
- `contacts` → single `organisation_id` (drop free-text org + dual client/lead FKs).
- Explicit relationship FKs: campaigns/client_invoices → client organisation;
  new supplier-side records → supplier organisation.
- Carry forward RLS, audit triggers, and constraints onto the new structure.
- Later (not now): `tasks` gains organisation_id + contact_id; a new `activities`
  table for the communications timeline.

Nothing here is built or decided — this is the discovery to challenge before 3.2.
