## 1. `organisations` — the master company entity
One row per real company. Replaces the split across clients / leads / free-text.

| Column | Notes |
|---|---|
| `id` | uuid pk |
| `name` | required |
| `sector` | from clients/leads today |
| `owner_id` | AdEx owner (drives restricted-user access) |
| `is_supplier` | boolean — independent of customer status |
| `customer_status` | enum (see §2) |
| `unique_ref` | Companies House no. or domain — prevents future dupes (§ discovery E-bis) |
| `archived` | boolean — operational visibility, **separate** from status (§4) |
| `created_at` | |

## 2. Customer lifecycle + history
`customer_status` enum: `prospect`, `active_client`, `former_client`,
`not_pursuing`, `none` (supplier-only / no customer relationship).

Status changes are **tracked events**, not overwrites, via a dedicated table
(not the 1.5 audit log — that's admin-only JSON with no reason field):

`organisation_status_history`: id, organisation_id, old_status, new_status,
changed_by, changed_at, reason (optional). Current status stays on the
organisation row for easy querying; history gives the timeline.

## 3. Contacts — people under an organisation
`contacts` gains `organisation_id` (required) and **drops** the free-text
`organisation` and the dual `client_id`/`lead_id` links. Keeps name, job title,
email, phone/mobile, LinkedIn. **Decision:** does contact-level `status` survive,
or is it derived from the organisation? (Recommend drop; the org carries status.)

## 4. Explicit commercial relationships (no generic `organisation_id`)
- `campaigns.client_org_id` → organisation (client side)
- `client_invoices.client_org_id` → organisation
- `creative_items.client_org_id` → organisation
- supplier side: a `supplier_org_id` on the supplier records (replacing today's
  free-text `vendor`). **Decision:** keep supplier channel tags (today's roster is
  per-channel) on the organisation or a small `organisation_channels` table.

## 5. Carrying the security controls across (mandatory, not optional)
- **RLS / 1.3:** restricted users see organisations they own; `can_see_client()`
  becomes `can_see_org()`; policies on campaigns/invoices/contacts re-derived
  against `client_org_id` / organisation ownership.
- **Audit / 1.5:** move `audit_trg` onto `organisations` (+ the status-history is
  itself a record); keep it on the financial tables.
- **Integrity / 1.4:** financial constraints unchanged; re-check any repointed FK.
- The `SECURITY_SELFCHECK.sql` gets new rows for the organisation controls.

## 6. Migration approach (execution detail depends on the data query)
1. Create `organisations` + history table (dev first).
2. Load organisations from `clients` (map status), then `leads` (map stage;
   **dedup against clients**), then distinct `vendor` names (is_supplier = true).
3. **Human dedup sign-off** on the merge list (you + Rick) — size TBD by the query.
4. Relink `contacts` by org-name → `organisation_id`; repoint
   campaigns/invoices/creative `client_id` → `client_org_id`.
5. Re-home the security controls (§5); run `SECURITY_SELFCHECK`.
6. Controlled cut-over, then retire the old `clients`/`leads` tables.

Likely split into sub-packages: **3.2** agree model · **3.3** build + migrate on
dev · **3.4** re-home security + cut-over. Too big for one step.

## 7. Decisions needed from Connor + Rick
- **Status mapping:** which current `clients.status` / `leads.stage` maps to which
  new `customer_status` (esp. what becomes "Former Client" / "Not Pursuing").
- **Unique identifier:** Companies House number vs website domain (recommend CH no.).
- **Contact status:** keep or drop (recommend drop).
- **Supplier channels:** tag suppliers by channel, or not.
- **PO numbering:** keep today's client-initials convention, or move to supplier-based.

## 8. Not now (the model just leaves room)
- `tasks` gaining organisation_id + contact_id.
- An `activities` table for the email/call/meeting timeline.
Both are enabled by this structure but built later.
