# Package 4.2 — Mailbox connection and the email timeline

**Status: PROPOSAL for Connor's approval. Nothing built yet.**
Dev only. No production change in this package.

---

## What this gives the team

Every organisation page — client or supplier — gains an **Email** section: the
messages between ADEX and that company, from every connected colleague's
mailbox, in one place. Who wrote, when, the subject, the first line, and a link
that opens the real message in Outlook.

Today that history lives in six separate inboxes. After this, "what did we last
say to Randox?" is one click on Randox.

Connecting is one action per person: **Settings → Connect mailbox → sign in with
your ADEX Microsoft login**. The same pattern as Xero, which the team has seen.

## Scope — deliberately thin, like 4.1

1. **Connect** — per-user Microsoft 365 sign-in (OAuth 2.0 via Microsoft Graph),
   admin-registered app, tokens locked away exactly as Xero's are.
2. **Read** — pull each connected mailbox's recent mail and keep only the
   messages that involve a known client or supplier (rule below).
3. **Show** — the Email section on the organisation page, and the sender's
   contact record where it matches one.

Then stop and review.

### Explicitly out of scope for 4.2
- **Sending** anything from the CRM (Space Orders to suppliers is 4.4)
- **Background sync** — see "the decision" below
- Storing message bodies or attachments
- Anything touching production or a real mailbox other than the testers' own

## The rule that makes this safe — needs Connor's agreement

**Only mail involving a known client or supplier is ever stored.**

A message is kept only if at least one sender or recipient is either
- a **contact** already in the CRM (matched on email address), or
- at an **organisation's domain** (`@randox.com`), where that domain is known
  from the organisation's existing contacts.

Everything else is read and discarded in the same moment: internal mail between
colleagues, personal mail, newsletters, suppliers who aren't in the CRM yet.
The CRM never holds a message it couldn't attach to a company you already track.

Consequence worth stating: the better the Organisations and Contacts data, the
better the timeline. Filling the shell (the Sage export) makes this work better.

## What is stored, per message

| Field | Why |
|---|---|
| Subject, date, from, to/cc | The timeline itself |
| First ~250 characters | Enough to recognise the message without opening it |
| Outlook link | Opens the real thing in the reader's own Outlook |
| Which organisation and contact it matched | The attachment point |
| Whose mailbox it came from | Provenance; also what "disconnect" acts on |

**Not stored:** the body, attachments, anything from a non-matching message.

The same message often sits in two colleagues' mailboxes (cc'd). It is stored
once, keyed on Microsoft's message identity, not twice.

## Who can see it

Full-staff users see the Email section on every organisation, because that is the
point — shared history. **Restricted users see none of it**, enforced by RLS the
same way commercial data is hidden from them today, not just by the page.

## Safety design — inherited from 4.1

- **Secrets server-side only.** `MS_CLIENT_ID` / `MS_CLIENT_SECRET` / `MS_TENANT_ID`
  without `NEXT_PUBLIC_`. Optional: the app runs unchanged if unset.
- **Tokens unreachable from the browser.** A `mail_connections` table (one row per
  user) with RLS on and **no policies**, reachable only through security-definer
  functions that check the caller is that user. Xero's exact pattern, per person.
- **Least permission.** `Mail.Read` (read the user's own mailbox), `User.Read`
  (who they are), `offline_access` (refresh without re-signing-in). No send, no
  other people's mail, no calendar, no files.
- **Disconnect** deletes that person's tokens immediately. Messages already
  attached to organisations stay — they are company history, not the person's —
  and that is stated on the button.
- **Dev testers only.** On dev, the only mailboxes connected are Connor's and
  Rick's, by their own choice, and only matched mail is kept. Nothing reaches
  anyone.

## The decision: how the sync runs

The security programme gave the CRM a property worth keeping: **no "god-mode"
key** — nothing runs except as a signed-in person, so RLS applies to everything.
Reading mail *in the background*, when nobody is signed in, would need such a
key. So 4.2 doesn't do that.

**Proposed for 4.2:** sync happens **when a connected person is using the CRM** —
on opening an organisation page (at most every 15 minutes per person) and via a
"Sync now" button in Settings. It runs as them, with their token, under their
session. Mail from everyone accumulates as everyone uses the app.

**Consequence:** a colleague who never opens the CRM contributes no mail until
they do. That is acceptable for a first slice, and it means this package changes
nothing about the security model.

**The daily brief (4.3) cannot work this way** — 7am has nobody signed in. That
package will need a scheduled job and a narrowly-scoped key for it, and will say
so in its own proposal rather than sneaking it in here.

## Microsoft set-up — what Connor needs to do

About ten minutes in the Microsoft 365 admin centre (Entra ID), walked through
screen by screen when we start:

1. **App registration** — single tenant (ADEX only), name "ADEX Mission Control".
2. **Redirect URIs** — both the dev preview and production addresses. Microsoft
   allows several on one registration, so unlike Xero this is one app, not two.
   Separate client secrets per environment.
3. **API permissions** — `Mail.Read`, `User.Read`, `offline_access` (delegated).
4. **Grant admin consent** — one click by Connor as admin, so each colleague's
   Connect is a sign-in and nothing more.
5. Paste client ID, tenant ID and a secret into Vercel as **Preview** variables.

## Acceptance criteria

| Criterion | Proven by |
|---|---|
| A user can connect and disconnect their own mailbox | Settings, both directions, Connor and Rick |
| Only matched mail is stored | Row count against a known inbox; an internal thread is absent |
| A cc'd message appears once | Same message from both testers' mailboxes → one row |
| Restricted user sees no Email section and no data | Test-restricted account; direct query refused by RLS |
| Tokens never reach the browser | Same check as 4.1 — no policy on the table, definer functions only |
| The app runs unchanged when Microsoft isn't configured | Production after merge, nothing set, no errors |

## Risks

- **Matching by domain over-catches** at big shared domains (a `@gmail.com`
  contact would match every Gmail sender). Domain matching applies only to
  domains that aren't public mail providers; those match on exact address only.
- **Volume** — a busy mailbox is thousands of messages. The first sync reads the
  last 90 days only; after that, changes since last time.
- **Consent policy** — some tenants block users consenting to apps. Admin consent
  in step 4 removes that entirely.
- **Token lifetime** — Microsoft refresh tokens last 90 days of inactivity. A
  colleague away that long reconnects; the page says so rather than failing.
